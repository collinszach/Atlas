## 1. Clear the PR pile-up  *(first, and it is mostly closing things)*

Four PRs are open and they are not four pieces of work. They are two pieces of work and two
attempts to verify them.

| PR | Branch | What it actually contains | Verdict |
|---|---|---|---|
| **#10** | `agent/atlas-120` | `test_logbook_distance.py` + `test_stats.py`, **plus** evidence docs. CI **green**. | **Merge.** It is the only one of the four carrying tests *and* a passing CI run. |
| **#6** | `agent/atlas-24` | The same two test files, 17 lines longer. Predates CI, so never ran it. | **Close as superseded by #10.** Diffed: #10 is #6 trimmed. |
| **#5** | `agent/atlas-23` | `test_adsb_contact_journey.py` + fixture. Real tests, **never verified** — opened 2026-11-09, CI landed 2026-11-10, so only Vercel ever ran on it. | **Re-run CI, then merge or fix.** Nothing else in the repo covers ADS-B staleness. |
| **#9** | `agent/atlas-119` | **Evidence documents only** — 652 lines, no code. | **Close.** See below. |

**Why #9 should be closed rather than merged, in detail**, because its green checkmark argues the
opposite. #9 exists to prove #5's tests pass. It cannot: its own evidence states the export
*"contains neither `backend/tests/test_adsb_contact_journey.py` nor the fixture"* — the tests it
was meant to verify are not in it. Worse, it reports `2 failed, 151 passed, 3 errors` against base
revision `89e7b68`, which is current `main`. CI on that exact SHA is **success**. The discrepancy
resolves as sandbox artifacts: both failures are `PermissionError`, and the three errors are
`test_skywatch_llm.py` setup errors — an agent sandbox with no database and no writable paths. So
#9 contributes a document that misreports the health of the suite, and its own CI is green only
because a docs-only diff runs `main`'s existing tests.

**The lesson worth keeping:** #9 and #81 both exist because at the time there was no trusted way to
run the tests. That is no longer the case. CI on a real runner is the evidence now, and hand-written
evidence documents should stop — `docs/evidence/` is already ~1,300 lines of superseded artifacts,
one of which (#81) records only `BLOCKED`.

**Net effect:** four open PRs become one merge, one re-run, two closes.

## 2. Make CI tell the truth  *(small, and it protects everything after)*

The pile-up above happened because results could not be trusted. Three gaps let that recur:

- **2a. No iOS job.** 9.3k lines of Swift and a 10-test suite that runs only when someone opens a
  laptop. Add a job: `xcodegen generate` then `xcodebuild test` on an iOS Simulator destination.
  Needs a macOS runner — if the `gs65-vm` fleet is Linux-only, this is the one item here that needs
  a decision rather than an afternoon.
- **2b. No sloplint gate.** `DESIGN.md` documents a Hallmark Floor and the exact command; nothing
  runs it. Wire the command already recorded in `DESIGN.md` § The one standing exclusion into the
  frontend job. It currently passes (1 FAIL, gate 20, excluded with reason), so it starts green.
- **2c. A docs-only PR can display "Backend tests = SUCCESS".** That is literally true and
  materially misleading, and it is exactly what made #9 look authoritative. Nothing in GitHub fixes
  this directly; the fix is the convention in §1 — verification lives in CI on the branch that
  carries the code, never in a separate PR.

  Clerk keys, domain-locked to `zacharyjcollins.com`. The app cannot run on localhost at all —
  `ClerkProvider` throws and the tree never mounts. Anyone cloning this repo is blocked on first

## 4. Then the product work

Only now is EPIC B worth starting, and it is unchanged from the spec: airframes as first-class
entities, every encounter against them, which joins the logbook to Skywatch and produces the
crossover nobody else can offer. Order within it is as the spec has it (B1→B7), with one note:
**B5 is the visible payoff** — flight cards finally rendering `A320 · N834JB` — so sequence it
early enough to be motivating rather than last.

A separate iOS defect worth folding in, found in the device log and unrelated to the life list:
**Apple Sign-In is broken at the Clerk configuration level.** Three logged failures,
`form_param_value_invalid`, *"oauth_token_apple does not match one of the allowed values for
parameter strategy"*. It is a dashboard fix, not a code fix, and `signInWithApple()` will keep
failing until someone enables Apple as a social connection in Clerk.
